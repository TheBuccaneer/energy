## Quick Start

### 1. Build
```bash
nvcc -O3 -std=c++17 -o gemm_bench main.cu -lcublas -lnvidia-ml
```

### 2. Run

### Measurement Details

- **Mode**: Always `e2e` (End-to-End with H2D/D2H transfers)
- **Batches**: Auto-determined per size to reach target runtime
- **seconds_gpu**: **Complete E2E GPU time** (H2D + Kernel + D2H) via CUDA events
- **seconds_wall**: Wall time for energy window (steady_clock)
- **energy_j**: NVML TotalEnergyConsumption delta in Joules (converted from mJ)
- **avg_power_w**: energy_j / seconds_wall
- **below_target**: `1` if gpu_time < target_runtime (batch limit hit), `0` otherwise
- **throttle_reasons**: NVML bitmask (0=none, 1=thermal, 2=power, 4=SW thermal, 8=HW slowdown, etc.)

## Key Features

### ✅ Buffer Reuse with LDA Trick
- Allocates once for max size (1536×1536)
- Smaller sizes use upper-left submatrix
- `lda = ldb = ldc = 1536` for all sizes
- **Much faster** than re-allocation per size

### ✅ Pinned Memory (Critical for Async Transfers)
- `cudaMallocHost()` for all host buffers
- **Enables true asynchronous H2D/D2H** via cudaMemcpy2DAsync
- Without pinned memory, async copies would degrade to synchronous
- Optimal H2D/D2H transfer bandwidth
- Critical for E2E measurements

### ✅ TF32 Disabled
- `cublasSetMathMode(handle, CUBLAS_DEFAULT_MATH)`
- Pure FP32 for reproducible comparisons

### ✅ Auto-Batch Sizing
- Per-size determination
- Ensures GPU time ≥ 1.0s (target)
- Respects MAX_BATCH_SIZE limit (200,000)
- **Flags below-target runs**: If MAX_BATCH_SIZE is hit but GPU time < 1.0s, sets `below_target=1`
  - Expected for very small matrices (64×64, 96×96)
  - Console shows `(!)` marker for these runs

### ✅ Complete E2E Timing
- **CUDA Events wrap entire E2E pipeline:**
  ```
  EVENT START
    → H2D transfers (async, pinned)
    → Kernel batches
    → D2H transfers (async, pinned)
  EVENT STOP
  ```
- `seconds_gpu` measures true E2E GPU time (not just kernel)
- All operations in same stream → sequential ordering guaranteed
- Events fire after all prior stream work completes

### ✅ NVML Energy + Telemetry
- **Energy**: `nvmlDeviceGetTotalEnergyConsumption` deltas
  - NVML returns cumulative mJ since driver reload
  - We calculate: `energy_j = (E_after - E_before) / 1000.0`
  - CSV stores in Joules for consistency with scientific conventions
- **Power**: `avg_power_w = energy_j / seconds_wall`
- **Throttle Detection**: `nvmlDeviceGetCurrentClocksThrottleReasons`
  - Bitmask: 0=none, 1=thermal, 2=power limit, 4=SW thermal, 8=HW slowdown
  - Logged per measurement for QC analysis
  - Console shows `THROTTLE=0xXX` if non-zero
- Clocks, temperature, PCIe state per measurement
- Overflow-safe (energy_after > energy_before check)

## Troubleshooting

### "NVML Error: Not Supported"
- **Cause**: Energy counter not available
- **Fix**: Driver R450+ required (RTX 3090 should be OK)
- **Note**: Tool sets energy_mj=0 and continues

### "CUDA out of memory"
- **Cause**: 1536×1536 too large (unlikely with RTX 3090's 24GB)
- **Fix**: Reduce MAX_SIZE in main.cu

### Batch size stuck at MAX_BATCH_SIZE (below target)
- **Cause**: Very small matrices can't reach 1.0s even with 60k batches
- **Indicator**: Console shows `(!)` and `below_target=1` in CSV
- **Expected**: For 64×64, 96×96, possibly 128×128 sizes
- **Impact**: Minimal - still generates valid energy measurements
- **Analysis**: Filter or analyze separately in QC pipeline (AP1b)

### Inconsistent energy readings
- **Cause**: Thermal throttling, power limit, unstable clocks
- **Check**: `throttle_reasons` column in CSV
- **Fix**: System stabilization (see AP3 Integration above)
- **Validation**: Temperature should be stable (±2°C during run), throttle_reasons=0

### Throttling detected (throttle_reasons != 0)
- **0x2 (Power Limit)**: GPU hitting 350W TDP
  - **Fix**: Increase power limit: `sudo nvidia-smi -pl 370` (if safe)
  - **Or**: Accept slightly lower clocks (still valid measurements)
- **0x4/0x8 (Thermal)**: GPU hitting temperature limit
  - **Fix**: Improve cooling, check airflow
  - **Critical**: If temp >80°C consistently
- **Impact**: Throttled runs have lower power but longer time
  - Energy measurement still valid
  - Flag these runs for separate analysis if needed

## Technical Details

### E2E Timing Architecture

**Measurement Pipeline:**
```
Wall Clock: |──────────────────────────────────────────|
            ↓                                          ↓
         t_start                                    t_end
            
Energy:     E0 ─────────────────────────────────────→ E1
            
GPU Stream: |──────────────────────────────────────────|
            ↓                                          ↓
         EVENT_START                             EVENT_STOP
            │                                          │
            ├─ H2D Transfer A (async, pinned)         │
            ├─ H2D Transfer B (async, pinned)         │
            ├─ Kernel Batch 1                         │
            ├─ Kernel Batch 2                         │
            ├─ ... (N batches)                        │
            ├─ D2H Transfer C (async, pinned)         │
            └──────────────────────────────────────────┘
                          ↓
              cudaDeviceSynchronize()
```

**Key Points:**
1. **Events are stream markers**, not host-side timestamps
2. `EVENT_STOP` fires only after D2H completes (stream ordering guarantee)
3. `cudaDeviceSynchronize()` waits for `EVENT_STOP` to fire
4. `seconds_gpu` = time between events (true GPU E2E)
5. `seconds_wall` = host time including small overhead
6. `energy_j` measured over same window as `seconds_wall`

### Why Pinned Memory Matters

**With Pinned Memory (our implementation):**
```
cudaMemcpy2DAsync():
  1. DMA engine copies directly from pinned host buffer
  2. Operation is truly asynchronous (returns immediately)
  3. Overlaps with other stream operations
  4. Full PCIe bandwidth (~16 GB/s on Gen3 x16)
```

**Without Pinned Memory (incorrect):**
```
cudaMemcpy2DAsync():
  1. CUDA allocates temporary pinned buffer
  2. Copies from pageable → pinned (blocking!)
  3. Then DMA transfer
  4. Operation becomes synchronous despite "Async" API
  5. Reduced effective bandwidth
```

**Our Implementation:**
- `cudaMallocHost()` at startup (once)
- Reuse for all measurements
- Guaranteed async behavior

### NVML Energy Counter Semantics

```cpp
// NVML returns cumulative energy in mJ since driver reload
unsigned long long E0 = nvmlDeviceGetTotalEnergyConsumption(device);
// ... GPU work ...
unsigned long long E1 = nvmlDeviceGetTotalEnergyConsumption(device);

// Energy for this job:
double energy_j = (E1 - E0) / 1000.0;  // mJ to J
```

**Important:**
- Counter may overflow (implementation-dependent)
- We check `E1 > E0` and reject negative deltas
- Counter resets on driver reload (log this!)
- Sampling rate: ~1ms (sufficient for 1+ second runs)

### Throttle Reasons Bitmask

```
throttle_reasons (unsigned long long):
  0x0000 = No throttling
  0x0001 = GPU Idle (not a problem)
  0x0002 = GPU clock limited by applications power draw
  0x0004 = GPU clock limited by SW Thermal Slowdown
  0x0008 = GPU clock limited by HW Thermal Slowdown  
  0x0010 = GPU clock limited by Sync Boost
  0x0020 = GPU clock limited by board power draw
  0x0040 = GPU clock limited by low voltage
```

**During measurements:**
- `0x0` expected (no throttling)
- `0x2` common near TDP limit (acceptable if stable)
- `0x4/0x8` indicates thermal issues (investigate!)
