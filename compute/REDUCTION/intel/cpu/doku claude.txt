# 📚 **Dokumentation: CPU Reduction Benchmark (OpenBLAS)**

## 1. **Überblick**

### Zweck
Messung von Zeit, Energie und Bandbreite für **Vektor-Reduktion** (Summation via DOT-Produkt) auf CPUs mit OpenBLAS, optimiert für Vergleichbarkeit mit GPU-Messungen.

### Operation
```cpp
result = sum(x[0..N-1])  // Implementiert als:
result = cblas_sdot(N, x, 1, ones, 1)  // DOT(x, 1ⁿ)
```

---

## 2. **Grundlegende Annahmen**

### 2.1 Messprinzipien
| Annahme | Begründung |
|---------|------------|
| **ONES-Vektor persistent** | Einmalig initialisiert, bleibt im Speicher → nur x-Vektor wird gelesen |
| **Zwei separate Modi** | `kernel` (nur DOT) vs. `e2e` (memcpy+DOT) → unterschiedliche Pass-Zahlen |
| **Target Runtime ~1s** | Kalibrierung auf 1.0s für statistisch robuste Messungen |
| **Median über Repeats** | 5 Wiederholungen → Median für Robustheit gegen Ausreißer |
| **Keine Doppel-Parallelisierung** | OpenBLAS-Threads explizit gesetzt, kein zusätzliches OpenMP |

### 2.2 Energie-Messung
| Annahme | Implementierung |
|---------|-----------------|
| **RAPL misst Package-Energie** | Nur `package-X` Zonen, keine Subdomains (core/uncore) |
| **Overflow pro Zone** | Jede Zone hat eigene `max_energy_range_uj` für Wrap-around |
| **Differenzen, keine Instant-Power** | `ΔE = after - before` (mit Overflow-Korrektur) |
| **Fehlerhafte Zonen überspringen** | Wenn `energy_uj = 0` oder `range = 0` → Zone ignorieren |

### 2.3 Bandbreiten-Semantik
| Modus | Bytes gezählt | Zeit gemessen | BW-Bedeutung |
|-------|--------------|--------------|--------------|
| **Kernel** | `2×N×4×passes` (x + ones) | DOT-Zeit | Effektive DOT-Memory-BW |
| **E2E (mixed)** | `1×N×4×passes` (nur memcpy) | memcpy+DOT Zeit | **Mixed BW** (nicht rein memcpy!) |
| **E2E (memcpy_only)** | `1×N×4×passes` (nur memcpy) | **nur memcpy** Zeit | Echte memcpy-BW (Sidecar-CSV) |

## 3. **Was wird gemacht? (Ablauf)**

### 3.1 Startup
```cpp
1. Parse --threads Parameter (Pflicht!)
2. openblas_set_num_threads(NUM_THREADS)
3. Discover RAPL zones (package-only)
4. Allocate aligned buffers (x, ones, work) - 64B via posix_memalign
5. Initialize:
   - x_max:    pseudozufällig (seed=42)
   - ones_max: fill with 1.0f (persistent!)
```

### 3.2 Pro N-Größe (19 Größen: 1M - 384M)
```cpp
FOR each N in N_SIZES:
  
  // Kalibrierung (getrennt für beide Modi)
  passes_kernel = calibrate(DOT-only, target=1.0s)
  passes_e2e    = calibrate(memcpy+DOT, target=1.0s)
  
  FOR rep in 1..REPEATS (=5):
    
    // ===== KERNEL MEASUREMENT =====
    energy_before = read_rapl_per_zone()
    t0 = steady_clock::now()
    
    FOR p in 1..passes_kernel:
      sum += cblas_sdot(N, x_max, 1, ones_max, 1)
    
    t1 = steady_clock::now()
    energy_after = read_rapl_per_zone()
    
    seconds_kernel = t1 - t0
    energy_kernel_j = Σ(per_zone_delta with overflow)
    
    // ===== E2E MEASUREMENT =====
    energy_before = read_rapl_per_zone()
    t0 = steady_clock::now()
    
    FOR p in 1..passes_e2e:
      if (E2E_INJECT_HOST_MEMCPY):
        memcpy(work_max, x_max, N*4)
        sum += cblas_sdot(N, work_max, 1, ones_max, 1)
      else:
        sum += cblas_sdot(N, x_max, 1, ones_max, 1)
    
    t1 = steady_clock::now()
    energy_after = read_rapl_per_zone()
    
    seconds_e2e = t1 - t0
    energy_e2e_j = Σ(per_zone_delta with overflow)
    
    // ===== OPTIONAL: MEMCPY-ONLY (if E2E_BW_MODE="memcpy_only") =====
    t0 = steady_clock::now()
    FOR p in 1..passes_e2e:
      memcpy(work_max, x_max, N*4)
    t1 = steady_clock::now()
    seconds_memcpy_only = t1 - t0
  
  END FOR (repeats)
  
  // Aggregation
  secK = median(seconds_kernel over repeats)
  secE = median(seconds_e2e over repeats)
  enK  = median(energy_kernel_j over repeats)
  enE  = median(energy_e2e_j over repeats)
  
  // Write 2 CSV rows (kernel + e2e)
  write_csv("kernel", secK, enK, bytes=2*N*4*passes_kernel, ...)
  write_csv("e2e",    secE, enE, bytes=1*N*4*passes_e2e, ...)
  
END FOR (N sizes)
```

## 5. **Unterschiede zur GEMM-CSV**

### 5.1 Feld-Semantik

| Feld | GEMM-Bedeutung | Reduction-Bedeutung | Unterschied |
|------|----------------|---------------------|-------------|
| **matrix_size** | M=N=K Dimension | `0` (N/A) | ⚠️ Vektor hat keine Matrix-Dim |
| **N** | (Nicht vorhanden) | Vektorgröße | ✅ Neues Feld |
| **bytes_total** | 2×(M×K + K×N + M×N)×4 | 2×N×4 (Kernel) oder 1×N×4 (E2E) | Unterschiedliche Formeln |
| **bw_gb_s** | Matrix-Memory-BW | DOT-Memory-BW | Unterschiedliche Operationen |

### 5.2 Neue Felder (nur Reduction)
```
- N               : Vektorgröße (nicht Matrix-Dimension)
- passes_kernel   : Kalibrierte Passes für Kernel-Modus
- passes_e2e      : Kalibrierte Passes für E2E-Modus
- seconds_kernel  : Explizite Kernel-Zeit (GEMM implizit)
- energy_kernel_j : Explizite Kernel-Energie
- avg_power_w_kernel : Kernel-Power
- avg_power_w_e2e    : E2E-Power
```

## 6. **Feld-Befüllungslogik (Detail)**

### 6.1 Modi-abhängige Felder

#### **Kernel-Zeile** (`mode=kernel`)
```cpp
batches        = passes_kernel
seconds_gpu    = seconds_kernel       // Immer Kernel-Zeit
seconds_wall   = seconds_kernel       // Im Kernel-Modus = Kernel
energy_j       = energy_kernel_j
avg_power_w    = energy_kernel_j / seconds_kernel
bytes_total    = 2 × N × 4 × passes_kernel  // Liest x UND ones
bw_gb_s        = bytes_total / seconds_kernel / 1e9
time_mode      = "kernel"
energy_mode    = "kernel"
includes_transfer = 0  // CPU hat nie PCIe-Transfer
```

#### **E2E-Zeile** (`mode=e2e`)
```cpp
batches        = passes_e2e
seconds_gpu    = seconds_kernel       // Immer noch Kernel (Vergleichbarkeit)
seconds_wall   = seconds_e2e          // E2E-Zeit (mit memcpy)
energy_j       = energy_e2e_j
avg_power_w    = energy_e2e_j / seconds_e2e

// Bytes: abhängig von E2E_INJECT_HOST_MEMCPY
if (E2E_INJECT_HOST_MEMCPY):
  bytes_total  = 1 × N × 4 × passes_e2e  // Nur memcpy-Bytes (nicht DOT!)
  bw_gb_s      = bytes_total / seconds_e2e / 1e9  // Mixed BW!
else:
  bytes_total  = -1  // Kein memcpy
  bw_gb_s      = -1

time_mode      = "e2e"
energy_mode    = "e2e"
includes_transfer = 0  // Immer 0 für CPU
```

### 6.2 Konstante Felder (alle Zeilen gleich)
```cpp
workload       = "reduction"
impl           = "openblas"
dtype          = "fp32"
seconds_target = 1.00
device_name    = cpu_model  // z.B. "Intel(R) Core(TM) i9-7900X"
gpu_name       = cpu_model  // (gleich, historische Gründe)
driver_version = "NA"
pcie_*         = "NA" / 0
clocks_*       = "NA"
throttle_reasons = 0
```

### 6.3 Fehlerwerte (`-1` Konvention)
```cpp
// Energie nicht verfügbar (RAPL-Fehler):
energy_j            = -1.0
avg_power_w         = -1.0
avg_power_w_kernel  = -1.0
avg_power_w_e2e     = -1.0

// Temperatur nicht verfügbar (hwmon fehlt):

// Kein memcpy im E2E-Modus:
bytes_total         = -1    // (CSV: "-1")
bw_gb_s             = -1.0  // (CSV: "-1")
```

### 6.4 Geteilte Felder (über Modi)
Beide Zeilen (kernel + e2e) pro N enthalten:
```cpp
passes_kernel      // Gleich in beiden Zeilen
passes_e2e         // Gleich in beiden Zeilen
seconds_kernel     // Gleich in beiden Zeilen (Median)

```

→ **Redundanz** für einfacheres Parsen ohne JOIN

## 7. **Spezialsemantik: E2E-BW-Mode**

### 7.1 Mixed Mode (Default: `E2E_BW_MODE="mixed"`)
```
bw_gb_s (e2e) = memcpy_bytes / (memcpy_time + DOT_time)
```
**Problem:** Misst NICHT reine memcpy-BW!

**Verwendung:** 
- Vergleich mit GPU-E2E (beide haben gleiche "mixed" Semantik)
- Zeigt **Gesamt-Overhead** durch Transfer

### 7.2 Memcpy-Only Mode (`E2E_BW_MODE="memcpy_only"`)
```
// Haupt-CSV: wie "mixed"
// Sidecar-CSV (reduction_cpu_openblas_memcpy.csv):
//   - 1 Zeile pro N (nur e2e-Mode)
//   - seconds_wall = pure memcpy time
//   - bw_gb_s = echte memcpy-BW
```

**Verwendung:**
- Trennung von memcpy-BW vs. DOT-BW
- Analyse von Memory-Subsystem-Performance

## 8. **Quality Gates & Validierung**

### 8.1 Eingebaute Checks
```cpp
below_target = 1 if seconds_gpu < 1.0s  // Warnung: zu kurz
```

### 8.2 Plausibilitätsbereiche (i9-7900X)

| Metrik | Erwartung | Grenze |
|--------|-----------|--------|
| **seconds_kernel** | 0.8 - 1.2s | < 0.5s oder > 2.0s → Fehler |
| **energy_kernel_j** | 30 - 70J | < 10J oder > 100J → RAPL-Fehler |
| **avg_power_w** | 40 - 70W | < 20W oder > 150W → Problem |
| **temp_c** | 50 - 70°C | > 80°C → Thermal-Issue |
| **bw_gb_s (kernel)** | 15 - 30 GB/s | > 100 GB/s → Bug |
| **bw_gb_s (e2e)** | 4 - 10 GB/s | > 50 GB/s → Bug |

### 8.3 Thread-Skalierung (erwartet)
```
Speedup(1T → 10T): 6-8× für große N
Speedup(10T → 20T): <1.2× (Hyperthreading-Limit)
```

## 10. **Wichtige Einschränkungen**

### 10.1 BW-Interpretation
- **bw_gb_s (kernel)**: Effektive DOT-Memory-BW (typisch 20-40% von STREAM)
- **bw_gb_s (e2e, mixed)**: **NICHT** reine memcpy-BW! (gemischte Last)
- Für reine memcpy-BW → `E2E_BW_MODE="memcpy_only"` verwenden

### 10.2 Energie-Messung
- RAPL misst **nur CPU-Package** (kein RAM, kein Chipset)
- Overflow-Behandlung ist **kritisch** (Counter = 18-Bit bei Intel)
- Fehlerhafte Zonen werden **übersprungen** (kein Abort)

### 10.3 Platform-Spezifika
- **Intel:** hwmon → `coretemp`
- **AMD:** hwmon → `k10temp`
- **RAPL-Pfad:** Erfordert Root oder `/sys/class/powercap` Permissions

## 12. **Zusammenfassung: Key Takeaways**

✅ **Was ist gut:**
- Energie-Messung robust (per-Zone Overflow-Handling)
- Median-Aggregation für statistische Robustheit
- Zwei-Modi-Messung (kernel vs. e2e) für faire GPU-Vergleiche
- Vollständige Metadaten in notes-Feld

⚠️ **Was beachten:**
- `bw_gb_s (e2e)` ist **mixed BW**, nicht reine memcpy-BW!
- `gpu_name` Feld heißt so, enthält aber CPU-Modell
- `includes_transfer=0` **immer** (CPU hat kein PCIe)
- Thread-Skalierung sättigt ab ~10 Threads (Memory-BW-Limit)

🎯 **Für Paper verwenden:**
- `bw_gb_s (kernel)` für DOT-Performance-Vergleiche
- `energy_j` für Energieeffizienz-Analysen
- Thread-Sweep (1-20T) zeigt HW-Limitierungen
- E2E-Overhead = `(seconds_e2e - seconds_kernel) / seconds_kernel`
